## 질문 1

고객 구매 금액 데이터가 오른쪽으로 심하게 치우친 분포를 보여요. 팀장님이 '평균 구매 금액이 5만원이니 다들 5만원 정도 쓴다고 보면 되겠네요'라고 말해요. 이 말에 어떻게 답할 건가요?

### 1) 리서치 메모

#### "오른쪽으로 심하게 치우친 분포 상태"로 구글링 {#research-skew .research-topic}

##### 1. 왜 '오른쪽으로 치우친 분포'라고 부를까요? {.research-detail}

- 꼬리의 방향: 데이터의 대부분은 왼쪽에 모여 있어서 왼쪽이 볼록하지만, 일부 큰 값들 때문에 오른쪽 꼬리가 길게 늘어집니다.
- 평균의 이동: 이 길게 늘어진 오른쪽 꼬리(큰 값들)가 평균값을 오른쪽으로 끌고 갑니다.

즉, "오른쪽으로 꼬리가 길게 늘어져 있다"는 의미에서 오른쪽으로 치우친 분포(Right-skewed) 또는 양의 왜도(Positive skewness)라고 부릅니다.

#### "평균으로 데이터를 사용할 시 주의점"으로 구글링 {#research-mean .research-topic}

##### 1. 아웃라이어(이상치)의 착시 효과 {.research-detail}

평균은 모든 데이터 값을 더해 개수로 나누기 때문에, 극단적으로 크거나 작은 값(Outlier)에 큰 영향을 받습니다.

- 예시: 9명이 연봉 3,000만 원을 받고 1명이 연봉 10억 원을 받는 회사에서, 구성원의 평균 연봉은 1억 2,700만 원이 됩니다. 이는 대다수 일반 직원의 현실(3,000만 원)을 잘 반영하지 못합니다.
- 보완책: 데이터의 치우침이 심할 때는 중앙에 위치한 값인 중앙값(Median)을 함께 확인해야 합니다.

##### 2. 데이터 분포의 형태 무시 {.research-detail}

평균은 데이터가 어떻게 퍼져 있는지(분포의 형태)를 보여주지 못합니다. 평균이 같더라도 실제 데이터의 양상은 완전히 다를 수 있습니다.

- 예시: 평균 수심이 1.2m인 계곡이라도, 어떤 곳은 10cm이고 어떤 곳은 3m 깊이일 수 있습니다. 평균만 믿고 들어갔다가는 위험에 처할 수 있습니다.
- 보완책: 데이터가 퍼진 정도를 나타내는 표준편차(Standard Deviation)나 분산을 함께 확인해야 합니다.

### 2) 내 답변

팀장님께는 “평균은 5만 원인데, 일부 고객의 큰 구매액 때문에 높게 나왔을 수 있습니다. 중앙값이랑 금액대별 고객 수도 한번 확인해 보겠습니다.”라고 말씀드릴 것 같습니다.

연봉 예시에서는 10명 중 9명이 3,000만 원을 받아도 평균은 1억 원이 넘습니다. 구매 금액도 이런 차이가 생길 수 있으니, 평균만 보고 대부분의 고객을 설명하기는 어렵다고 생각합니다.

그래서 평균이 틀렸다고 하기보다는, 평균과 실제 고객들이 많이 쓰는 금액이 다를 수 있다는 점을 설명하겠습니다. 중앙값으로 중간 수준을 보고, 금액대별 고객 수로 어디에 사람이 많이 모여 있는지 확인해서 같이 보여드리겠습니다.

구매액이 큰 고객도 그냥 빼지는 않겠습니다. 입력이 잘못된 건지, 실제로 많이 구매한 건지 먼저 봐야 한다고 생각합니다. 실제 구매라면 그 금액을 포함한 평균도 남기고, 다른 수치와 같이 보겠습니다.

## 질문 2

서로 다른 두 팀이 각자 관리하던 고객 데이터를 하나로 합쳐야 해요. 두 데이터 모두 고객 ID가 중복되거나 값이 다르게 기록된 행이 있고, 결측치도 섞여 있어요. 어떤 순서로 이 작업에 접근할 건가요?

### 1) 리서치 메모

#### "중요한 2개의 테이블을 합칠 때 주의해야 할 점"으로 구글링 {#research-merge .research-topic}

##### 병합 전: 데이터 구조 및 품질 분석 {.research-detail}

- 원본 데이터 백업: 운영 서버나 메인 데이터베이스에서 직접 작업하지 말고, 반드시 임시 테이블(Temporary Table)이나 스테이징 구역에서 먼저 작업을 수행하세요.
- 데이터 타입 일치 확인: 조인의 기준이 되는 키(Key) 컬럼의 데이터 타입이 일치하는지 확인해야 합니다. 한쪽은 INT인데 다른 쪽은 VARCHAR라면 형 변환 오류나 매칭 실패가 발생할 수 있습니다.
- Key 컬럼의 데이터 정제: 기준 컬럼에 공백, 대소문자 차이, 특수문자가 포함되어 있는지 확인하세요. 예를 들어 "Apple "과 "Apple"은 서로 다른 데이터로 인식될 수 있습니다.
- 키의 중복과 대응 관계 파악: 1:1, 1:N, N:N 관계 중 어떤 구조인지 미리 파악해야 합니다. 특히 N:N 관계에서 무작정 조인하면 같은 키를 가진 행들이 서로 조합되는 카테시안 곱(Cartesian Product)으로 행 수가 크게 늘어날 수 있습니다.
- 인덱스(Index) 확인: 대용량 테이블을 합칠 경우, 조인 키 컬럼의 인덱스를 확인하세요. 인덱스가 성능에 도움이 될 수 있지만, 데이터 규모와 처리 방식에 따라 효과가 달라집니다.

##### 병합 후: 데이터 정밀 검증 {.research-detail}

- Row Count(행 수) 비교: 병합 전후의 행 수를 반드시 비교하세요. LEFT JOIN을 했는데 원본 테이블보다 행 수가 늘어났다면, 상대 테이블의 매칭되는 키에 중복이 있다는 뜻입니다.
- 집계 수치(Aggregations) 검증: 동일한 거래·고객 범위를 비교할 때는 병합 전 테이블의 주요 수치(예: 총 매출액, 총 회원 수)와 병합 후 결과물의 수치가 일치하는지 교차 검증하세요. 데이터 중복으로 인해 금액이 뻥튀기되는 오류를 잡을 수 있습니다.
- 샘플링 테스트: 병합된 결과물에서 상위, 하위, 중간 데이터를 몇 건 골라 원본 데이터와 직접 눈으로 대조하는 작업을 거치세요.

### 2) 내 답변

먼저 원본을 따로 저장해 두고, 각 표에서 한 행이 어떤 기록인지 확인하겠습니다. 고객 한 명당 한 줄인 표인지, 같은 고객의 구매 기록이 여러 줄인 표인지에 따라 중복의 의미가 달라질 것 같기 때문입니다. 같은 고객 ID를 두 팀이 같은 사람에게 쓰고 있는지도 확인하겠습니다.

그다음에는 고객 ID의 자료형과 공백 같은 표기 차이를 맞추겠습니다. ID가 여러 번 나온다고 바로 지우지는 않겠습니다. 같은 기록이 두 번 들어간 것인지, 서로 다른 기록인지 먼저 보겠습니다.

같은 고객인데 값이 다르면 어느 쪽을 남겨야 할지 담당자에게 물어보겠습니다. 최근 자료라는 이유만으로 무조건 맞다고 볼 수는 없으니, 어느 자료를 기준으로 할지 먼저 정해야 할 것 같습니다. 결측치도 다른 팀 자료에서 같은 고객의 값으로 채울 수 있는지 보겠습니다. 확인이 안 되면 일단 비워 두고, ID가 없는 행은 따로 빼서 확인하겠습니다.

이렇게 정리한 뒤 표를 합치고, 행 수와 고객 수가 예상한 만큼 나오는지 보겠습니다. 합쳐진 표에 같은 고객이 불필요하게 여러 번 들어가거나 정보가 빠지지는 않았는지 확인하고, 몇 건은 원본과 직접 비교하겠습니다. 금액 합계도 같은 거래와 기간을 기준으로 비교해야 할 것 같습니다.

저는 이 작업에서 중복이나 빈칸을 빨리 없애려다가 필요한 정보까지 지우는 것을 가장 조심해야 할 것 같습니다. 바꾼 부분과 아직 확인이 안 된 부분은 따로 적어 두겠습니다.
